# Hospital Vital Signs Monitoring (Edge-to-Cloud)

**Distributed Systems for IoT**

An academic distributed IoT project for monitoring simulated patient vital signs. Three simulated monitors publish pulse and SpO2 readings over MQTT. The Edge layer, implemented with Node-RED, processes readings, detects abnormal values and displays alerts on a dashboard. The Cloud layer forwards readings to Apache Kafka, where independent Python consumers store historical measurements and calculate averages using SQLite.

This is an academic simulation. There are no real patients and the system is not intended for medical use.

## 1. System Architecture

The system is divided into two independent processing paths:

- **Edge:** Node-RED receives MQTT readings, evaluates alert thresholds and displays alerts on a dashboard.
- **Cloud:** A Python bridge forwards MQTT messages to Kafka. Two independent Kafka consumers process the readings and store the results in SQLite.

```text
                 SIMULATED MONITORS
                         |
                         v
                  MQTT (Mosquitto)
                         |
              +----------+----------+
              |                     |
              v                     v
          EDGE PATH             CLOUD PATH
              |                     |
           Node-RED          Python MQTT-Kafka
              |                  Bridge
       Alert Detection              |
              |                     v
          Dashboard               Kafka
                                    |
                           hospital-readings
                                    |
                         +----------+----------+
                         |                     |
                         v                     v
                   history-writer       avg-calculator
                         |                     |
                         v                     v
                      readings              averages
                         +----------+----------+
                                    |
                                  SQLite
```

The Edge alert path does not depend on Kafka. Therefore, Kafka failures do not directly stop the Node-RED alert processing path.

## 2. Docker Services

The Docker Compose environment includes four services:

| Service | Description |
|---|---|
| `mosquitto` | MQTT message broker |
| `nodered` | Monitor simulator, alert logic and dashboard |
| `kafka` | Apache Kafka broker running in KRaft mode |
| `kafka-ui` | Web interface for inspecting Kafka topics and consumer groups |

The Python Cloud processes run independently on the host machine using a Python virtual environment.

## 3. MQTT Communication

Readings are published every 10 seconds using QoS 1.

### MQTT Topics

The topic structure is:

`hospital/{ward}/room{room}/{sign}`

Examples:

- `hospital/ward2/room204/pulse`
- `hospital/ward2/room204/spo2`
- `hospital/ward2/room205/pulse`
- `hospital/ward2/room205/spo2`
- `hospital/ward2/room206/pulse`
- `hospital/ward2/room206/spo2`

### MQTT Message Format

Each reading is published as a JSON message:

```json
{
  "ward": "ward2",
  "room": "204",
  "patient": "P001",
  "sign": "pulse",
  "value": 72,
  "unit": "bpm",
  "timestamp": "2026-11-13T20:35:15.271Z"
}
```

| Field | Description | Example |
|---|---|---|
| `ward` | Ward identifier | `ward2` |
| `room` | Room number | `204` |
| `patient` | Patient identifier | `P001` |
| `sign` | Type of measurement | `pulse` or `spo2` |
| `value` | Measurement value | `72` |
| `unit` | Measurement unit | `bpm` or `%` |
| `timestamp` | Reading generation time (UTC, ISO 8601) | `2026-11-13T20:35:15.271Z` |

The timestamp is generated by the simulator. The Cloud bridge preserves the original JSON payload and timestamp when forwarding messages to Kafka.

### Patient Mapping

| Patient | Room |
|---|---|
| P001 | 204 |
| P002 | 205 |
| P003 | 206 |

### Alerts

Alerts are published to:

`alerts/{ward}/room{room}`

QoS: 1.

Only state changes are published:

- `ALERT`: pulse below 40 bpm or above 140 bpm, or SpO2 below 90%.
- `RESOLVED`: measurements return to normal.

The topic `status/monitors` is retained and reports `online` or `offline` when Node-RED disconnects, using MQTT Last Will functionality.

## 4. Cloud Architecture

### 4.1. MQTT-to-Kafka Bridge

File: `consumers/mqtt_kafka_bridge.py`

The bridge is implemented in Python using:

- `paho-mqtt` for MQTT communication.
- `confluent-kafka` for Kafka message production.

It subscribes to all vital-sign readings using the MQTT wildcard:

`hospital/+/+/+`

Each received message is forwarded to the Kafka topic:

`hospital-readings`

The patient identifier (`patient`) is used as the Kafka message key. This ensures that messages with the same key are consistently assigned to the same partition, preserving their order within that partition.

The original JSON payload is preserved.

### 4.2. Kafka Configuration

| Parameter | Configuration |
|---|---|
| Broker | Single Kafka broker |
| Topic | `hospital-readings` |
| Partitions | 3 |
| Replication factor | 1 |
| Message key | `patient` |
| Message value | Original JSON payload |

Kafka connection addresses:

- From Docker containers: `kafka:29092`
- From Windows: `localhost:9092`

The replication factor is 1 because the project uses a single Kafka broker.

### 4.3. Kafka Consumers

Two independent Python consumers subscribe to `hospital-readings`. They use different consumer groups, so each group processes the complete message stream independently.

**History Writer**

File: `consumers/history_writer.py`

- Consumer group: `history-writer`
- Reads vital-sign messages from Kafka.
- Stores individual readings in SQLite.
- Uses `INSERT OR IGNORE` and a composite primary key to prevent duplicate records.

SQLite table: `readings`

| Field | Description |
|---|---|
| `patient` | Patient identifier |
| `sign` | Measurement type |
| `timestamp` | Original reading timestamp |
| `value` | Measurement value |
| `unit` | Measurement unit |
| `ward` | Ward identifier |
| `room` | Room number |

The primary key consists of `patient`, `sign` and `timestamp`.

**Average Calculator**

File: `consumers/avg_calculator.py`

- Consumer group: `avg-calculator`
- Reads the same Kafka topic independently.
- Groups readings by patient, measurement type and time window.
- Calculates averages when a time window closes.
- Stores the results in SQLite using `INSERT OR REPLACE`.

The default calculation window is 60 seconds. It can be changed using the `WINDOW_SECONDS` environment variable.

SQLite table: `averages`

| Field | Description |
|---|---|
| `patient` | Patient identifier |
| `sign` | Measurement type |
| `window_start` | Beginning of the time window (Unix timestamp) |
| `average` | Calculated average |
| `unit` | Measurement unit |

### 4.4. SQLite Database

Both consumers use the same SQLite database:

`history.db`

The database connection and table creation are centralized in:

`consumers/database.py`

This module provides the `get_database()` function, which is imported by both consumers.

The database contains two tables:

- `readings`: individual historical measurements.
- `averages`: calculated averages for each time window.

The database file is generated locally and is not included in Git.

## 6. How to Run

### 6.1. Start the Docker Environment

From the project root:

```powershell
copy .env.example .env
docker compose up -d --build
```

Check the running services:

```powershell
docker compose ps
```

This starts Mosquitto, Node-RED, Kafka and Kafka UI.

### 6.2. Create the Kafka Topic

Kafka topic auto-creation is disabled. Create the topic explicitly:

```powershell
docker exec iot_kafka kafka-topics --bootstrap-server kafka:29092 --create --topic hospital-readings --partitions 3 --replication-factor 1
```

To inspect its configuration:

```powershell
docker exec iot_kafka kafka-topics --bootstrap-server kafka:29092 --describe --topic hospital-readings
```

If the topic already exists, Kafka will report that it exists; it does not need to be recreated.

### 6.3. Install Python Dependencies

Open a PowerShell terminal in the project root:

```powershell
cd consumers
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

If the virtual environment already exists, activate it and install any missing dependencies.

### 6.4. Run the Cloud Processes

Each Python process must run in a separate terminal. Activate the virtual environment in each terminal.

**Terminal 1 – MQTT-to-Kafka Bridge**

```powershell
cd consumers
.\.venv\Scripts\Activate.ps1
python mqtt_kafka_bridge.py
```

**Terminal 2 – History Writer**

```powershell
cd consumers
.\.venv\Scripts\Activate.ps1
python history_writer.py
```

**Terminal 3 – Average Calculator**

```powershell
cd consumers
.\.venv\Scripts\Activate.ps1
python avg_calculator.py
```

To change the average calculation window:

```powershell
$env:WINDOW_SECONDS = "120"
python avg_calculator.py
```

### 6.5. Access the Interfaces

| Interface | URL |
|---|---|
| Node-RED | http://localhost:1880 |
| Dashboard | http://localhost:1880/dashboard |
| Kafka UI | http://localhost:8080 |

### 6.6. Monitor MQTT Messages

To inspect incoming vital-sign readings:

```powershell
docker exec -it iot_mosquitto mosquitto_sub -t "hospital/#" -v
```

To inspect alerts:

```powershell
docker exec -it iot_mosquitto mosquitto_sub -t "alerts/#" -v
```

### 6.7. Inspect Kafka Consumer Groups

To inspect the history consumer:

```powershell
docker exec iot_kafka kafka-consumer-groups --bootstrap-server kafka:29092 --describe --group history-writer
```

To inspect the average calculator:

```powershell
docker exec iot_kafka kafka-consumer-groups --bootstrap-server kafka:29092 --describe --group avg-calculator
```

The `LAG` column indicates how many messages remain to be processed by each consumer group.

## 7. Recovery and Reprocessing

Kafka consumer groups maintain independent offsets. If a consumer stops, its pending messages remain available according to Kafka's retention configuration.

When the consumer restarts, it can continue processing from its last committed offset.

The history writer uses `INSERT OR IGNORE` to avoid duplicate historical records when messages are processed again.

The average calculator can also reprocess messages by resetting its consumer group offset to the beginning, provided the consumer is stopped first:

```powershell
docker exec iot_kafka kafka-consumer-groups --bootstrap-server kafka:29092 --group avg-calculator --topic hospital-readings --reset-offsets --to-earliest --execute
```

The calculator can then be restarted with a different `WINDOW_SECONDS` value to recalculate averages using a new window size.
